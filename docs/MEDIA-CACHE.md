# Generated media cache contract

Mounted unavailable generated images retry automatically: three short retries followed by 30-second backoff, capped at ten attempts; unmounting clears timers. Galleries poll pending/evicted representations until they become ready. Folder-demand discovery resumes direct pending work whose prior scan was cancelled; permanent processing failures still require explicit retry.

`POST /api/media/priority` carries the media a person is looking at, in the order it is displayed, starting at the top of the viewport and continuing past it. The gallery, viewer and Reels send it; the batch is bounded to 200 IDs, resent only when that ordered set changes, and retried a bounded number of times after a failed request. Each position is queued separately so preparation follows that order rather than media ID, and a later request supersedes an earlier one without starving it. The request only updates existing processing jobs: media whose prior scan was cancelled or interrupted is adopted by a scan that can run it, so search results spanning folders are prepared without revisiting each folder. Media with no runnable scan in its library is left alone. Nothing here enumerates directories, reads originals or generates media during a browse request.

Generation, persistence and maintenance are implemented in stage 3; HTTP serving and visible-item regeneration requests are implemented in stage 4. Browse requests use generated files only, even when originals are unavailable.

Variants version 1: thumbnail (WebP, longest edge 320 px, quality 75), preview (JPEG, longest edge 1920 px, quality 85), video poster (JPEG, longest edge 1280 px, quality 80). Do not upscale. Flatten alpha onto the shared neutral background for JPEG. Use the first GIF frame/TIFF page. Video poster uses the lesser of 10% duration or 3 seconds, falling back to the first decodable frame. Retain dimensions of both original and generated media. Animated previews and video transcodes are out of scope.

Cache identity is `(mediaId, sourceRevision, variant, encoderVersion)`. Use sharded ID directories under configured cache storage; paths never depend on user filenames. Write to a unique temporary file on the same filesystem, validate output and length, then atomically rename and commit ready state. Crash recovery removes stale temporary files and reconciles orphaned published files in bounded background batches. Never publish a partial file. Recheck source revision before committing a job; discard stale output.

Source changes and variant-version changes invalidate old representations. Keep old files only until cleanup; never serve a stale revision as current. Source disappearance alone does not invalidate cache. Normal serving validates generated file availability, not the source; use content hash ETag and immutable caching for versioned URLs. URLs with an obsolete revision return 404. An absent, failed or corrupt current entry returns Problem Details 503 `cache_unavailable` with `Retry-After: 30`; UI displays a placeholder. The handler sends a disposable hint to a bounded background channel and never waits for a SQLite write or processing. Its consumer upserts deduplicated durable work, skipping already pending/running jobs. A missing source leaves regeneration pending until availability returns. Background verification checks corruption. The UI does not request known pending images and polls bounded summaries until they become ready; evicted representations still issue visible-item regeneration requests.

Default quota: 20 GiB; configurable minimum 1 GiB. Reserve 1 GiB free disk; stop generation if either threshold would be crossed. Maintain byte accounting in SQLite, reconcile it periodically by bounded cache-only enumeration. Cleanup starts at 90% quota and targets 80%, evicting least-recently-used previews before thumbnails/posters; batch access-time updates (at most once per item per hour). Keep current small representations where space permits; quota does not guarantee every item fits. Deleted/obsolete revisions and temporary files go first. Avoid an eviction/regeneration loop: under pressure only explicit visible-item demand requeues evicted entries. Report pressure in administrative status. Cache is disposable; deletion followed by background regeneration is supported. Never remove originals.

## Stage 3 implementation details

Generation reserves 48 MiB per active job (two output files bounded below 16 MiB each, plus the optional video frame), in addition to the configured free-disk reserve. Quota accounting is maintained by SQLite triggers. Cache-only verification uses keyset batches of 100 records; filesystem orphan checks use batches of 100 names. Unique temporary/orphan files older than ten minutes are removed, allowing active jobs to finish. Revision/version-obsolete entries are removed before quota eviction.

Indexing prepares only the thumbnail for an image; its preview is prepared on demand, when the viewer, Reels, `/api/random` or a preview URL asks for it (`WantPreview` on the job, ahead of background work). Until then the client shows the browser-decodable original over its thumbnail, and keeps it for that visit rather than swapping when the preview arrives. A video job owns thumbnail + poster. Migration 16 released the previews earlier releases generated for every image; thumbnails, tags and covers were kept, so upgrades need no re-index. Cache verification checks file length (the SHA-256 remains the ETag) in a full sweep at startup and then daily; the quota check runs every interval. Loss/corruption deduplicates regeneration at the `(mediaId, sourceRevision, encoderVersion)` job, generating its two representations together. Evicted entries keep a zero-byte state row and are not automatically requeued by verification or unchanged scans. Regeneration of evicted visible content and batched access-time recording arrive with the stage 4 serving endpoint; until then, publication time initializes LRU order. A forced scan explicitly regenerates all representations.
