# Generated media cache contract

Generation, persistence and maintenance are implemented in stage 3; HTTP serving and visible-item regeneration requests remain stage 4. Browse requests use generated files only, even when originals are unavailable.

Variants version 1: thumbnail (WebP, longest edge 320 px, quality 75), preview (JPEG, longest edge 1920 px, quality 85), video poster (JPEG, longest edge 1280 px, quality 80). Do not upscale. Flatten alpha onto the shared neutral background for JPEG. Use the first GIF frame/TIFF page. Video poster uses the lesser of 10% duration or 3 seconds, falling back to the first decodable frame. Retain dimensions of both original and generated media. Animated previews and video transcodes are out of scope.

Cache identity is `(mediaId, sourceRevision, variant, encoderVersion)`. Use sharded ID directories under configured cache storage; paths never depend on user filenames. Write to a unique temporary file on the same filesystem, validate output and length, then atomically rename and commit ready state. Crash recovery removes stale temporary files and reconciles orphaned published files in bounded background batches. Never publish a partial file. Recheck source revision before committing a job; discard stale output.

Source changes and variant-version changes invalidate old representations. Keep old files only until cleanup; never serve a stale revision as current. Source disappearance alone does not invalidate cache. Normal serving validates generated file availability, not the source; use content hash ETag and immutable caching for versioned URLs. URLs with an obsolete revision return 404. An absent, failed or corrupt current entry returns Problem Details 503 `cache_unavailable` with `Retry-After: 30`; UI displays a placeholder. The handler may upsert one deduplicated pending job in SQLite but cannot process it or wait for processing. A missing source leaves regeneration pending until availability returns. Background verification checks corruption; client-reported decode failures can request deduplicated regeneration with rate limiting.

Default quota: 20 GiB; configurable minimum 1 GiB. Reserve 1 GiB free disk; stop generation if either threshold would be crossed. Maintain byte accounting in SQLite, reconcile it periodically by bounded cache-only enumeration. Cleanup starts at 90% quota and targets 80%, evicting least-recently-used previews before thumbnails/posters; batch access-time updates (at most once per item per hour). Keep current small representations where space permits; quota does not guarantee every item fits. Deleted/obsolete revisions and temporary files go first. Avoid an eviction/regeneration loop: under pressure only explicit visible-item demand requeues evicted entries. Report pressure in administrative status. Cache is disposable; deletion followed by background regeneration is supported. Never remove originals.

## Stage 3 implementation details

Generation reserves 48 MiB per active job (two output files bounded below 16 MiB each, plus the optional video frame), in addition to the configured free-disk reserve. Quota accounting is maintained by SQLite triggers. Cache-only verification uses keyset batches of 100 records; filesystem orphan checks use batches of 100 names. Unique temporary/orphan files older than ten minutes are removed, allowing active jobs to finish. Revision/version-obsolete entries are removed before quota eviction.

A ready image job owns thumbnail + preview; a video job owns thumbnail + poster. Loss/corruption deduplicates regeneration at the `(mediaId, sourceRevision, encoderVersion)` job, generating its two representations together. Evicted entries keep a zero-byte state row and are not automatically requeued by verification or unchanged scans. Regeneration of evicted visible content and batched access-time recording arrive with the stage 4 serving endpoint; until then, publication time initializes LRU order. A forced scan explicitly regenerates all representations.
